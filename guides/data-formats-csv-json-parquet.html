CSV vs JSON vs Parquet

The format you store data in affects file size, speed, accuracy and who can open it. Here's how to choose.

CSV: the universal handshake

Comma-separated values is the lowest common denominator. Every spreadsheet, database and programming language can read it. That universality is why open-data portals publish CSV first.

Its weaknesses all stem from having no schema. A CSV doesn't know that 00501 is a ZIP code, not the number 501. It has no standard for dates, encodings or even delimiters (much of Europe uses semicolons because the comma is the decimal separator). Quoting rules (RFC 4180) handle commas and line breaks inside fields, but hand-made files often break them. Always specify UTF-8 encoding and an unambiguous date format when you publish CSV.

JSON: structure for applications

JSON represents nested structure naturally: an order containing a customer object and an array of line items. That's why almost every web API speaks JSON. It distinguishes numbers, strings, booleans and null, which removes some of CSV's ambiguity.

The cost is size and flatness. Field names repeat in every record, and analysis tools usually want a flat table. Converting JSON to a table means flattening: nested keys become dotted column names (customer.country), and arrays either become separate rows or stay as text. Our CSV ⇄ JSON Converter flattens automatically.

Variant: JSON Lines (NDJSON) stores one JSON object per line. It's ideal for logs and streaming, because files can be appended to and processed line by line.

Parquet: built for analytics

Apache Parquet stores data by column rather than by row. When a query needs only three of fifty columns, it reads only those three. Similar values sit together, so compression is excellent. Files are often a fraction of the size of the equivalent CSV. Parquet also stores a schema, so types survive the round trip.

Parquet is the default for data lakes and is read natively by modern engines and libraries (Spark, DuckDB, pandas, Polars and cloud warehouses). The trade-off: you can't open it in a text editor or a basic spreadsheet, so it's a poor choice for sharing with non-technical colleagues.

Excel: the business interface

Spreadsheets are where most business data starts and ends. They support formatting, formulas and multiple sheets. They're also where merged cells, hidden rows, inconsistent types and silent auto-conversion (gene names turned into dates is a famous example) creep in. Treat .xlsx as a presentation format and keep a clean, typed source of truth elsewhere.

How to choose

  • Sharing a table with anyone, anywhere? CSV, UTF-8, ISO dates, with a short README describing columns.
  • Feeding a web app or API? JSON.
  • Logs or event streams? JSON Lines.
  • Millions of rows for analysis? Parquet.
  • Handing a report to a manager? Excel or a dashboard, generated from a clean source.
